Spatial networks

Networks on maps

A spatial network consists of

  • nodes (points): e.g. intersections, stations, municipalities
  • edges (lines) between nodes: e.g. roads, rail links, flows

Examples: road and river networks, public transport, origin-destination (OD) flows such as commuting and migration

sfnetworks

The package sfnetworks combines

  • sf: spatial data (nodes and edges are sf objects)
  • tidygraph / igraph: graph analysis (shortest paths, centrality, …)
library(sfnetworks)
sfn = as_sfnetwork(roxel)
class(sfn)
[1] "sfnetwork" "tbl_graph" "igraph"

tmap.networks

The extension package tmap.networks (in development):

  • supports sfnetwork objects natively as a shape in tm_shape()
  • adds network specific layers:

Network measures computed with tidygraph can be mapped directly:

      fill.legend = tm_legend("Degree"))

Using network analysis

Parts of edges: from and to

from and to (between 0 and 1) determine which part of each edge is drawn:

tm_shape(sfn) +
    tm_edges(col = "type", lwd = 4, from = 0.3, to = 0.4) +
    tm_nodes()

Useful for directed networks: e.g. drawing only the half of each edge near its destination.

Origin-destination flows

Commuting in the Netherlands

  • An OD matrix: number of jobs by municipality of residence (from) and municipality of work (to)
  • Municipality centroids as nodes

muni = read.csv2("data/NL_municipality_centroids_2024.csv") |>
  st_as_sf(coords = c("POINT_X", "POINT_Y"), crs = 28992)

Building the network

edges = od |>
  filter(from != to, jobs >= 2000) |>          # no self-flows, only large flows
  mutate(from = match(from, muni$code),         # codes -> node row indices
         to   = match(to,   muni$code))

net = sfnetwork(nodes = muni, edges = edges, directed = TRUE, edges_as_lines = TRUE)
  • sfnetworks requires from and to as row indices of the nodes
  • edges_as_lines = TRUE: straight lines between the node locations
  • Filtering is essential: the full OD matrix has more than 73,000 pairs

A flow map

Problems with flow maps

  • Direction is not visible: A → B and B → A are drawn on top of each other
  • Clutter: many lines crossing, especially around large cities
  • Visual hierarchy: long lines attract attention, regardless of their volume

Solutions:

  • filter (minimum flow), aggregate, or highlight
  • half lines: draw only the destination half of each edge (from = 0.5)
  • control the drawing order of the edges (plot.order)

Half lines

tm_shape(NLD_prov) +
  tm_polygons("grey95", col = "grey70") +
tm_shape(net) +
  tm_edges(
    lwd = "jobs",
    col = "steelblue",
    from = 0.5,
    lineend = "butt",
    lwd.scale = tm_scale_continuous(values.scale = 5),
    lwd.legend = tm_legend("Commuters")) +
  tm_nodes(size = 0.1)

Each edge is drawn from its middle to its destination: the direction is encoded by position.

Half lines

Edge options

opt_tm_edges():

  • offset_start, offset_end: offset (in map coordinates, usually meters) of the start and end points, e.g. to keep edges out of the node symbols

Other tm_edges() arguments:

  • lineend ("round", "butt", "square") and linejoin
  • plot.order: by default, edges are ordered by line width (tm_plot_order("lwd", reverse = TRUE))

Donuts and half lines

A design space for OD data

Tennekes and Chen (2021) organise all (theoretically) possible visualisations of OD data in a design space:

  • Decompose the data into its components: origins, destinations, and the flows between them (volume and direction)
  • List the options for each component: e.g. positioned geographically (map) or in an abstract layout (matrix, grid); flow shown as a line, a matrix cell, or a part of a glyph
  • Each combination of options is a visualisation method: known methods (flow maps, OD matrices, OD maps, chord diagrams) are points in this space
  • Unexplored combinations suggest new methods: this is how the half lines (combined with donuts at the nodes) came about

Discuss: which method shows direction, volume and geography best? Could you build a design space for another data type?

Tennekes M, Chen M (2021). Design Space of Origin-Destination Data Visualization. Computer Graphics Forum 40(3), 323–334 (EuroVis 2021).

Combining glyphs and networks

Donut maps with half lines (Tennekes and Chen, 2021):

  • Donuts at the nodes (municipality of work):
    • size: total number of jobs
    • slices: where the workers come from — four highlighted cities, the municipality itself (home), or other
  • Half lines for the flows:
    • width: number of commuters
    • color: the destination category, drawn from the middle of the edge to the destination (from = 0.5)

Tennekes M, Chen M (2021). Design Space of Origin-Destination Data Visualization. Computer Graphics Forum 40(3), 323–334 (EuroVis 2021).

Data preparation

The preparation is done by helper functions in R/commuting.R:

  • categorise(): classifies municipalities as one of the highlighted cities, "home" or "other"
  • aggregate_od(): aggregates the OD flows per node, one column per donut slice, plus the Total
  • build_network(): builds the directed sfnetwork with the node data joined, and removes self-loops and flows below edge_min
source("R/commuting.R")

od = read.csv2("data/NL_commuter_OD_2024.csv")
name_highlight = c("Amsterdam", "Rotterdam", "Den Haag", "Utrecht")

net_nodes = build_network(od, muni, name_highlight, flow = "jobs", edge_min = 500)

The donut map

library(tmap.glyphs)
palette = c("#d9328a", "#7d4791", "#da5914", "#53a31d", "#0581a2", "#B3B3B3")
bb_randstad = st_bbox(c(xmin = 60000, xmax = 175000, ymin = 405000, ymax = 505000), crs = 28992)

tm_shape(net_nodes, bbox = bb_randstad) +
  tm_edges(
    lwd        = "Jobs",
    col        = "to_cat",
    from       = 0.5,
    lineend    = "butt",
    lwd.scale  = tm_scale_continuous(values.scale = 8),
    col.scale  = tm_scale_categorical(values = palette, value.neutral = palette[5]),
    col.legend = tm_legend_hide(),
    options    = opt_tm_edges(offset_start = 100)) +
  tm_donuts(
    parts       = tm_vars(c(name_highlight, "other", "home_part"), multivariate = TRUE),
    size        = "Total",
    size.scale  = tm_scale_continuous(
      values.scale   = 1.2,
      limits         = c(30000, 750000),
      ticks          = c(30000, 100000, 250000, 700000),
      labels         = c("\u2264 30,000", "100,000", "250,000", "\u2265 750,000"),
      outliers.trunc = c(TRUE, FALSE),
      values.range   = c(0.3, 0.75)),
    fill.scale  = tm_scale_categorical(
      values        = palette,
      value.neutral = palette[6],
      labels        = c(name_highlight, "other", "home")),
    fill.legend = tm_legend(title = "Municipality"),
    size.legend = tm_legend(title = "Jobs by workplace"),
    col         = "white",
    lwd         = 1,
    options     = opt_tm_donuts(fill_hole = "gray95")) +
tm_basemap("Esri.WorldGrayCanvas")

The donut map

What happens here?

  • net_nodes is an sfnetwork: tm_edges() uses the edge data, tm_donuts() the node data
  • home_part is used for the slices: it is zero for the highlighted cities, whose own workers are already in their named slice
  • Size scale: limits, ticks and custom labels; outliers.trunc = c(TRUE, FALSE) truncates values below 30,000 to the smallest size
  • value.neutral: the (grey/blue) color used in the size and line width legends
  • opt_tm_edges(offset_start = 100): offset of the start points, in map units (here meters)

Design choices

  • Same palette for slices and edges: the color of a line matches the highlighted city it flows to
  • "other" and "home" in blue and grey, so the four highlighted cities stand out
  • A muted basemap ("Esri.WorldGrayCanvas") keeps the context subordinate
  • Zoomed in on the Randstad with bbox: the rest of the country could be an inset (session 10)
  • Sizes are tuned per mode: in "view" mode, sizes are relative to the screen (pixels), in "plot" mode relative to the map size — so values.scale differs
